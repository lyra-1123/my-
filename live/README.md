# MT5 模拟盘实时程序

把 `paper/specs.py` 里已登记的策略接到 MT5 **模拟账户**上自动下单。信号用与模拟盘完全相同的代码（`paper.engine.compute`）计算，只是数据来源换成 MT5 的实时 K 线。

## 文件
| 文件 | 作用 |
|---|---|
| `live/config.py` | 配置：品种名、服务器时区、各策略的启用/魔术号/手数、点差上限、熔断等（**唯一需要改的文件**） |
| `live/check_mt5.py` | 上线前第 1 步：检查账户、合约、时区、历史深度，可选与 Dukascopy 对齐 |
| `live/compare_signals.py` | 上线前第 2 步：同一段时间用 MT5 数据和 Dukascopy 数据分别算信号，比较是否一致 |
| `live/runner.py` | 实时程序：每根 30 分钟 K 线收盘后运行一次 |
| `live/daily_review.py` | 每日复盘数据层：读取 MT5 成交记录，与模型逐笔对照，输出 `live/reports/review_<交易日>.md` 和 `daily_summary.csv` |
| `live/selftest.py` | 自测（不需要 MT5，用 Dukascopy 数据模拟服务器），在云端/任何机器上都能跑 |
| `live/logs/` | `decisions.csv`（每次决策）、`orders.csv`（每笔订单与回执）、`state.json` |

## 每次运行做什么
每个 UTC :00 / :30 过 8 秒，对每个启用的策略：
1. 从 MT5 取最近的 K 线（30MIN 策略取 M30，1H 策略取 H1），服务器时间换算成 UTC，丢掉还没走完的那根；经纪商历史常有大段缺失，只用最后一个缺口（> 5 天）之后的连续数据，连续数据不足 `MIN_BARS` 时该策略不交易；
2. 计算目标仓位（+1 / 0 / −1）× 手数；
3. 按魔术号查这个策略的实际持仓，不一致就先平后开（市价单）；
4. 影子版本 HA1H-TS2 在服务器端设置移动止损（每根 1H K 线更新一次）；
5. 写日志。

1H 策略在 :30 那次运行时发现 K 线没变，直接跳过。成交时点与模型一致：信号在 K 线收盘确定，下一根开盘附近成交。

## 在 Windows 电脑上的准备（一次性）
1. 安装 Python 3.10+，然后：`pip install MetaTrader5 pandas numpy scipy`
2. 拉取本仓库（分支 `claude/nifty-edison-y4dkuq`），在仓库根目录打开命令行。
3. MT5 终端：
   - 登录 **对冲（hedging）模式的模拟账户**。4 个策略用魔术号区分各自的仓位，净额（netting）账户会把它们合并成一个仓位，程序会拒绝运行。
   - 工具 → 选项 → 图表 → "图表中最大K线数" 设为 **无限**（或 ≥ 100000），然后重启终端。
   - 工具 → 选项 → 智能交易 → 勾选"允许算法交易"，并且工具栏上的"算法交易"按钮是绿色的。
   - 在"市场报价"里确认黄金的品种名。如果不是 `XAUUSD`（例如 `XAUUSD.`、`XAUUSDm`），就改 `config.py` 的 `SYMBOL`。
4. 按需修改 `live/config.py`（手数、要启用哪些策略等）。

## 上线步骤
**第 1 步：检查环境**
```
python -m live.check_mt5 --dukascopy-dir "C:\Users\Lyra\Desktop\策略\黄金\数据"
```
`--dukascopy-dir` 填 Dukascopy M1 CSV 所在的文件夹。它会给出 5 项结果，逐项确认：
- 模拟账户：True，对冲模式：True；
- 合约大小 100（0.01 手 = 1 盎司）。如果不是，按比例调整 `lots`；
- 时区"一致"：要在开盘时间运行，休市时实测偏移不可靠；
- 历史深度"足够"；
- 滞后相关：**最佳滞后必须是 +0.0 小时**。如果最大值出现在 ±1 小时，就把 `SERVER_TZ` 改成 `"fixed:+2"`、`"fixed:+3"` 之类，再测一次。

**第 2 步：比较信号**
```
python -m live.compare_signals --dukascopy-dir "C:\...\数据" --days 60
```
事先写死的通过标准：目标仓位一致率 ≥ 90%，且 z 相关 ≥ 0.90。
- 没通过的策略，在 `config.py` 里设 `enabled: False`，先不上线，把结果发给我。
- 最可能出问题的是 TT30 和 MF30：它们用到成交量，MT5 给的是 tick_volume，Dukascopy 是另一种量。HA1H 只用价格，应当几乎完全一致。

**第 3 步：运行**
```
python -m live.runner
```
- 保持命令行窗口和 MT5 终端都开着。电脑不能睡眠，可以在电源设置里关掉。
- 也可以用 `python -m live.runner --once` 只跑一次，配合 Windows 任务计划程序在每个 :00 / :30 过 10 秒触发。

## 风控与开关
| 机制 | 说明 |
|---|---|
| 只允许模拟账户 | `DEMO_ONLY=True`，连到真实账户直接退出 |
| 紧急停止 | 在仓库根目录新建一个名为 `live/STOP` 的空文件，下一次运行会平掉本程序的全部仓位，之后不再开仓。删除文件即恢复 |
| 组合熔断 | `DAILY_LOSS_LIMIT_USD`：当日（纽约 17:00 起）本程序所有仓位的已实现 + 浮动亏损超过该值，就平仓并暂停到下一交易日。默认关闭（None），数值等"组合熔断"研究完成后再定 |
| 点差保护 | 点差 > `MAX_SPREAD_USD` 时不开新仓，平仓照常 |
| 数据中断保护 | 最新完整 K 线距现在超过 35 分钟（休市、断线）时不操作 |
| 手动干预 | 不要手动改本程序开的单（按魔术号识别）。手动平掉后，程序会在下一根 K 线按目标重新开回来 |

启动时默认不立即对齐仓位（`ALIGN_ON_START=False`），等下一根 K 线收盘再操作，与模型的成交时点一致。

## 日志怎么看
- `live/logs/decisions.csv`：每策略每根 K 线一行，包括 z、目标、当前手数、动作（HOLD / OPEN_LONG / OPEN_SHORT / CLOSE / REVERSE_* / ERROR）、止损、点差、数据延迟和备注。
- `live/logs/orders.csv`：每笔订单的请求价、成交价、回执码（10009 = 成功）。
- 实盘表现和模型账本的差异（滑点、点差、止损成交价）会在前向评估时用这两个文件核对。请定期把 `live/logs/` 发给我或提交到仓库。

## 已知差异（与模型账本相比）
1. **数据源**：模型用 Dukascopy BID，实盘用经纪商报价。价格差很小，但成交量不同，所以 TT30、MF30 会有少量信号差异（第 2 步量化）。
2. **成交价**：模型按下一根开盘价、固定点差 0.2 计；实盘是市价单真实成交，含滑点和经纪商的实际点差和过夜费。
3. **影子版本 HA1H-TS2 的止损**：模型按 1H 最高/最低价触发，实盘由服务器按 tick 触发，结果基本一致。新开仓时，模型的初始止损以"下一根开盘价"为基准，实盘以开仓时的 BID 为基准。
4. **30MIN/1H 策略每天纽约 17:00 前平仓**（避开过夜费），与模型一致。

## 每日复盘
- runner 在每个交易日收盘（纽约 17:00，北京时间夏令时 05:00 / 冬令时 06:00）后的第一次运行，自动生成前一交易日的 `live/reports/review_<交易日>.md`（`AUTO_DAILY_REVIEW=True`）。
- 手动生成或补做：`python -m live.daily_review --day 2026-09-29`（不带 `--day` = 最近一个已收盘交易日）。
- 内容：当日行情；各策略实际 / 按 0.2 点差折算 / 模型盈亏；规则检查（手动干预、报错、下单失败、过夜、仓位一致率、滑点、延迟，阈值写死）；逐笔明细（参考价、延迟、扣点差后的滑点、MFE/MAE、兑现率、R）；上线以来累计 vs 登记区间；必须解释的偏离。
